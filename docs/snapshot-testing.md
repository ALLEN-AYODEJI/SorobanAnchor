# Local snapshot update workflow

Regression snapshots live in the `test_snapshots/` directory at the repository
root. A snapshot is a JSON record of what a contract test observed: auth
entries, contract calls and arguments, generated addresses, and related
serialized fields.

Snapshots are useful because they make an unexpected change visible in a diff.
They are only useful if a human reviews each change. **Accepting generated
output without reading it is not an adequate review.** A snapshot that is
regenerated without inspection can hide the regression it was meant to catch.

## Layout

Each snapshot is stored at:

```text
test_snapshots/<test-file-name>/<test-name>.<n>.json
```

- `<test-file-name>` is the integration test file without `.rs`. For example,
  `tests/session_tests.rs` writes to `test_snapshots/session_tests/`.
- `<test-name>` is the test function name.
- `<n>` is a counter that the test environment assigns to each snapshot a
  test produces. Some tests have more than one, such as `.1.json` and
  `.2.json`.

## Step 1: Run the focused test

Run only the test whose snapshot you are reviewing. This example uses the
session replay snapshot test in `tests/session_tests.rs`:

```bash
cargo test --test session_tests test_recorded_anchor_session_replay_is_reproducible_offline -- --nocapture
```

The test environment refreshes the snapshot files for that test when it runs.

## Step 2: Check which files changed

```bash
git status --short test_snapshots/
```

If no file is listed, the snapshot matches the committed version and there is
nothing to review.

## Step 3: Inspect the diff

```bash
git diff -- test_snapshots/session_tests/
```

Review the serialized fields, not only the line count:

- **Function names and arguments** in the `auth` and invocation entries. Do
  they match the call sequence your code change intends?
- **Contract and account addresses**. Are the same addresses used across
  runs, or did a generated address change without a code change?
- **Generator and nonce values**. A change here with no related code change
  can indicate non-deterministic setup.
- **Ledger and event data** that the test asserts on. Do the values match the
  behavior you expect?

## Step 4: Decide whether the change is expected

Ask one question: can you explain every changed field from your code change?

- **Yes, the change is intended.** Stage the snapshot with the code change so
  that reviewers see both together:

  ```bash
  git add test_snapshots/session_tests/
  ```

- **No, or you are not sure.** Restore the committed snapshot and investigate
  the test or the code before continuing:

  ```bash
  git checkout -- test_snapshots/session_tests/
  ```

  Only run this on files you have not edited on purpose, because it discards
  the generated changes.

## Things not to do

- Do not delete or regenerate all of `test_snapshots/` in one step. A bulk
  regeneration hides which change caused which difference.
- Do not accept a snapshot diff you have not read.
- Do not hand-edit generated snapshot files to match a failing assertion.
  Fix the code or the test instead.

Some fixtures are read by tests and are not regenerated by running them. For
example, `tests/transaction_state_tracker_tests.rs` loads files from
`test_snapshots/transaction_state_tracker_tests/`. Change these only by hand,
with the same review described above.
